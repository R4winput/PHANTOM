# Architecture

## Current milestone

The initial milestone establishes a Rust workspace and a minimal version-reporting CLI. It deliberately does not implement networking, cryptography, invitation handling, or chat persistence.

## Crate boundaries

| Crate | Owns | Must not own |
| --- | --- | --- |
| `phantom-cli` | Argument parsing, user-facing output, command dispatch | Wire protocol details or cryptographic primitives |
| `phantom-core` | Session lifecycle and coordinating domain operations | Socket implementation or UI concerns |
| `phantom-network` | Connection setup, transport, relay integration | Plaintext storage or session policy |
| `phantom-crypto` | Ephemeral identities and cryptographic operations | Networking and logging of secrets |
| `phantom-protocol` | Versioned message types and serialization boundaries | Network sockets or user interface |
| `phantom-coordinator` | Invitation validation and signaling as an independent service | Message plaintext and peer private keys |

Keep dependencies directed and acyclic. `phantom-protocol` is the shared boundary between participants and the coordinator. The coordinator is a separately deployable binary, not a process that must run on either participant's machine.

## Intended connection path (future work)

1. Attempt a direct QUIC connection.
2. Attempt libp2p NAT traversal.
3. Use an explicitly documented relay fallback when direct connectivity fails.

QUIC is the preferred transport, not a guarantee that UDP is available. The relay must forward opaque, authenticated ciphertext and must not become a plaintext endpoint. Metadata exposure and relay trust assumptions require further design review before networking is implemented.

## Future session lifecycle

An invitation is short-lived and single use. A joining peer receives a fresh identity for the session. Peers authenticate the connection, exchange encrypted messages with replay protection, and tear down session resources when a participant exits. No chat history is generated by PHANTOM. Exact key agreement, message authentication, wire encoding, expiry rules, and memory handling must be specified and reviewed before those features land.

## Deferred design

The first network milestone targets two peers. Group sessions and membership changes are deferred; later group messaging should use OpenMLS instead of a home-grown group cryptographic protocol. Encrypted file transfer is also deferred.
